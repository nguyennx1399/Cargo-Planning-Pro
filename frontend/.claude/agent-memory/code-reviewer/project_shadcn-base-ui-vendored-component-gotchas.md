This repo's shadcn install (`shadcn@latest`, style "base-nova") generates on `@base-ui/react` (Base UI), not Radix. Two real bugs/gaps were found in the vendored `src/components/ui/*.tsx` wrappers (not hand-edited by the team, except alert.tsx's warning variant) during review of the CSS-class-to-shadcn migration (App.tsx, Sidebar.tsx, StabilityPanel.tsx, LoadingSequencePanel.tsx, OffsetsImportPanel.tsx, ParticularsForm.tsx, FairnessWarningsList.tsx).

**Slider duplicate-thumb bug**: `src/components/ui/slider.tsx`'s `_values` fallback (`Array.isArray(value) ? value : Array.isArray(defaultValue) ? defaultValue : [min, max]`) only handles array-valued `value`/`defaultValue`. For the common single-thumb controlled pattern `<Slider value={someNumber} onValueChange={...} />` with no `defaultValue`, it falls through to `[min, max]` (2 elements), rendering 2 overlapping `<Slider.Thumb>` DOM elements. Both resolve to `index=0` internally (Base UI's `SliderThumb` does `index = !range ? 0 : ...`, and `range = Array.isArray(valueUnwrapped)` is false for plain-number value), so they stay in sync and don't crash, but it's a real duplicate/overlapping DOM node — doubles tab stops, visual z-fighting risk. Confirmed by reading `node_modules/@base-ui/react/slider/root/SliderRoot.js` and `slider/thumb/SliderThumb.js`. Fix: either pass `defaultValue={[min]}`-shaped hint, or (better) fix the wrapper's `_values` line to `: Array.isArray(defaultValue) ? defaultValue : typeof value === "number" ? [value] : [min, max]`.

**Slider loses accessible name for Label+htmlFor sibling pattern**: Unlike Checkbox (see below), `SliderRoot`'s `id`/`aria-labelledby` land on the root wrapper `<div>` only. The actual focusable element is `Slider.Thumb`, whose `aria-labelledby` comes from Base UI's own `<Slider.Label>` child-registration or an explicit `aria-labelledby` prop threaded through context — there is NO sibling-`<label htmlFor>` auto-detection (confirmed: no `useAriaLabelledBy`/`findAssociatedLabel` call in `SliderRoot.js`, unlike CheckboxRoot). So the shadcn-idiomatic `<Label htmlFor="x"><Slider id="x" /></Label>`-as-siblings pattern silently produces a Thumb with no accessible name. Fix: pass `aria-labelledby` explicitly on `<Slider>` pointing at an `id` given to the sibling `<Label>` (not just relying on `htmlFor`/`id` pairing, which does nothing here).

**Checkbox+Label sibling pattern DOES work correctly** (verified, don't flag as a bug): `CheckboxRoot` renders a `<span role="checkbox">` plus a visually-hidden native `<input id={controlId}>` as siblings. Base UI's `useAriaLabelledBy`/`findAssociatedLabel` (`internals/labelable-provider/useAriaLabelledBy.js`) specifically detects a `nextElementSibling` `<label>` whose `htmlFor` matches the hidden input's id, and wires `aria-labelledby` onto the visible span at runtime via a layout effect. So `<Checkbox id="x" /><Label htmlFor="x">...</Label>` as siblings (the pattern used throughout Sidebar.tsx/StabilityPanel.tsx) is correctly accessible, including native label-click-to-toggle (browser forwards the click to the hidden input). Don't waste review time re-deriving this — it required reading Base UI internals to confirm since it looks suspicious on the surface (label targets a hidden `aria-hidden` input, not the visible control).

**ToggleGroup semantic downgrade** (inherent to the component, not a coding mistake): Base UI's `ToggleGroup` renders `role="group"` and each `Toggle` is a `<button aria-pressed>`, not `role="radiogroup"`/`role="radio" aria-checked` like a hand-rolled single-select control would use. This is the same in Radix's ToggleGroup — it's a known trade-off of this component family, not something introduced by this migration. Worth a passing mention in reviews but not a regression to block on.

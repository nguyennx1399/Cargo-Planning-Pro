Phase 01-02 review (2026-09-12) of `plans/260912-0117-cargo-type-catalog-breakbulk/phase-01-cargo-catalog-data-model.md` and `phase-02-breakbulk-area-placement.md`. Full report: `plans/260912-0117-cargo-type-catalog-breakbulk/reports/code-reviewer-phase-01-02-cargo-catalog-breakbulk.md`. 316/316 tests green, typecheck clean at review start.

**Critical finding — breakbulk ship-frame x uses `vessel.length_m` (LOA), rest of codebase uses `geometry.particulars.lbp_m` (LBP) — diverge by exactly (length_m−lbp_m)/2 = 6m on the demo vessel (length_m=172, lbp_m=160).**
`engine/breakbulk-deck-area.ts` (`deckArea`) and `engine/breakbulk-forbidden-zones.ts` (`bayCenterXShipFrame`) both treat ship-frame x as `[0, vessel.length_m]`. The established convention (`lib/ship-frame.ts`'s `shipToScene`/`sceneToShip`, used by `lib/cargo-weight-item.ts`, the whole hull/hydrostatics engine) anchors x=0 at AP using `geometry.particulars.lbp_m`, not LOA. `domain.ts`'s own doc comment for `BreakbulkPlacement.x_m` says "ship-frame x ... from AP" — same wording as `ship-frame.ts`, implying the wrong (LBP) convention was intended.
**Why:** `deckArea`/`breakbulk-forbidden-zones.ts` were deliberately written to avoid depending on `VesselGeometry` (plan.md Key Insight: breakbulk shouldn't require a vessel to have full geometry) — but the chosen fallback silently assumes `lbp_m == length_m`, which is false for any real ship (and false for the demo vessel specifically, which DOES have a `geometry_id` attached with `lbp_m=160 != length_m=172`).
**Confirmed as a live bug, not theoretical**: `engine/cargo/breakbulk-mesh-builder.ts` (phase-03 code that appeared in the tree mid-review) renders every breakbulk item via `shipToScene(geometry, [x_m, ...])` = `x_m - lbp_m/2` (real lbp_m=160), while containers render via `ContainerInstances.tsx` → `bayCenterX(vessel, bay)` called WITHOUT geometry (always the `length_m`-symmetric fallback). Net: a breakbulk item placed by `naiveFillBreakbulk` to just clear an on-deck-container zone will render ~6m further toward the bow than the collision math assumed — can visually clip into the container it was placed to avoid. `breakbulk-mesh-builder.test.ts`'s alignment test only self-checks against `shipToScene` (tautological), never cross-checks against where a container actually renders — this gap is untested.
**How to apply:** when reviewing phase-03/04 of this plan, check whether this was fixed — either (a) make breakbulk geometry-aware (`geometry?.particulars.lbp_m ?? vessel.length_m`, matching `VesselScene.tsx`'s own existing fallback pattern) end-to-end including `breakbulk-mesh-builder.ts`, or (b) make `breakbulk-mesh-builder.ts` convert scene position the same way `ContainerInstances.tsx` does (`x_m - vessel.length_m/2`, NOT `shipToScene`+real lbp_m) to stay self-consistent with container rendering. Either is fine; what's NOT fine is the current state where deck-area/collision math and the renderer use two different origins. Also recheck: does `vessel.length_m` vs `geometry.particulars.lbp_m` mismatch (LOA vs LBP, always differs when a vessel has overhangs) recur anywhere else new code is added that reasons in "ship-frame x" without going through `ship-frame.ts`'s helpers.
